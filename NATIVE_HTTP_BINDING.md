# Bind empty HTTP 202 responses before rule evaluation

The first development observation records eight real Figshare dataset targets returning HTTP 202 after DOI redirects, with empty stored response bodies. The three authored controls return HTTP 404. These are actual current responses, without a source-loss or anti-bot-mechanism inference. No final-group landing or reference has been inspected.

[RFC 9110, section 15.3.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3) defines 202 as acceptance for processing, without completed processing. The protocol already separates request status, independently observed landing context and data-file access. Make that distinction explicit in the implementation: an empty 202 is `accepted_not_completed`, not evidence of a rendered dataset landing or downloadable files. Other 2xx responses are only observed HTTP responses until their context is checked. A 204 similarly does not provide a rendered page. Data-file availability stays `not_tested` throughout.

This native-status binding occurs before development rule/metric calculation and final observations. It does not alter any captured status, introduce a learned threshold, select a favorable candidate or classify a dataset as missing. The naive comparator remains the declared non-2xx/failure rule; the conservative DOI-review action still requires two uncensored 404/410 observations at the declared time separation. Preserve accepted/incomplete states and independent browser reference labels separately. The original protocol and first raw/sanitized snapshots remain unchanged.
